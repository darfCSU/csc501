# Module 4: Project Design and Outline
## Frosmear Legacy Modernization

**Company:** Schumann Hudson Acquisition & Technology (SHAT)  
**Project:** Frosmear Legacy Modernization  
**Target Platform:** Darfcloud, built with Docker, Django, and MySQL  
**Project Start Date:** October 1, 2026  
**Target Completion Date:** December 23, 2026  
**Estimated Duration:** 12 weeks  
**Estimated Budget:** $210,000

## 1. Project Scope and Goals

The Frosmear Legacy Modernization project will transform the existing PHP-based Frosmear website into Darfcloud, a modern, cloud-oriented application platform. The project will establish a maintainable foundation using Docker containers, the Django web framework, and a MySQL database.

The initial release will focus on authentication, user permissions, application navigation, integration with relevant legacy functionality, data migration, security controls, backups, and deployment. The platform will provide a foundation for future artificial intelligence concepts, general-purpose applications, and investment-analysis tools. Advanced applications and additional business features will be considered for future development increments in FY2027 unless approved through the project's change-control process.

Two specialized teams will support the modernization effort. **LAME (Legacy Application Maintenance Engineering)** will focus on legacy PHP compatibility, preservation of relevant functionality, migration dependencies, and protection of the delivery schedule. **PITA (Protection, Integrity, Threat Assessments)** will focus on authentication, authorization, data integrity, security risks, and protection against unauthorized access or misuse of the authentication handoff.

Project success will be measured by completion of the agreed functionality, successful validation of migrated account data, satisfaction of security requirements, completion of required testing, and acceptance of the deployed system by the designated stakeholders.

## 2. Project Timeline and Major Deliverables

The project will run from October 1 through December 23, 2026. The schedule uses overlapping activities to meet the aggressive 12-week target. Marketing has insisted that delivery occur before 2027, so the project team must coordinate closely and resolve blockers quickly. Overlapping work will require coordination between the core development team, LAME, PITA, and operations.

| Project Phase | Duration | Start Date | Completion Date | Major Deliverables |
|---|---:|---|---|---|
| 1. Planning | 2 weeks | October 1, 2026 | October 14, 2026 | Project charter, scope statement, budget, schedule, stakeholder plan |
| 2. Current System Assessment | 2 weeks | October 8, 2026 | October 21, 2026 | Legacy inventory, requirements, migration assessment, LAME compatibility review |
| 3. Architecture and Environments | 2 weeks | October 15, 2026 | October 28, 2026 | Docker/Django/MySQL architecture, environment standards, PITA security requirements |
| 4. Application Development | 4 weeks | October 22, 2026 | November 18, 2026 | Authentication, permissions, application menu, legacy integration |
| 5. Data Migration and Security | 3 weeks | November 5, 2026 | November 25, 2026 | Migrated accounts, provisioning procedures, LAME compatibility validation, PITA security controls, backup and recovery procedures |
| 6. Testing and Deployment | 2 weeks | November 26, 2026 | December 9, 2026 | Functional, security, and integration test results; production deployment; operational handoff |
| 7. Project Closeout | 2 weeks | December 10, 2026 | December 23, 2026 | Acceptance approval, documentation, lessons learned, maintenance plan |

The schedule is aggressive and depends on timely decisions, adequate staffing, and early identification of technical problems. Current-system assessment begins before planning is completely finished, while migration and security activities overlap with application development. LAME will identify legacy dependencies early so they do not become late-stage surprises. PITA will review security requirements throughout development rather than waiting until final testing.

These activities can proceed in parallel where dependencies permit, but critical prerequisites must be satisfied before testing and production deployment. The project manager will track cross-team dependencies and escalate issues that threaten the December 23 completion target.

Regular communication will include status reports, milestone reviews, issue escalation, and demonstrations of completed functionality. Stakeholder feedback will be documented and evaluated rather than automatically becoming additional project scope.

## 5. Change Requests and Goal Alignment

Changes to project requirements, schedule, budget, or deliverables will be documented and evaluated before approval. Each request will be assessed for its effect on project scope, cost, schedule, technical dependencies, security, and expected business value.

The project manager will coordinate the evaluation. The CTO will assess technical implications, PITA will review security-related changes, LAME will assess effects on legacy compatibility and migration, and the CFO will evaluate financial impacts. Significant changes to the approved project baseline will require authorization from the project sponsor or designated steering committee.

This process is intended to prevent scope creep and protect the December 23, 2026, completion target. For example, a request to add an advanced artificial intelligence application during the initial release would be evaluated against available resources, security requirements, and delivery commitments. If the change threatens the core modernization goals, it should be deferred to a future increment.

Similarly, LAME may identify a legacy feature that requires more work than expected, while PITA may identify a security control that cannot be deferred. The project manager must evaluate the schedule and cost implications of these findings without treating compatibility or essential security as optional. If a significant adjustment is necessary, the project sponsor must approve the revised baseline.

The project aligns with SHAT's objectives by reducing dependence on legacy technology, improving maintainability and security, and establishing a scalable foundation for future applications. Delivering the platform in phases will provide opportunities to identify problems early, incorporate stakeholder feedback, and make informed decisions before final deployment.

## 6. Maintenance and Project Closeout

Following deployment and acceptance, operational responsibility will transition to the designated operations team. Ongoing maintenance will include system monitoring, security updates, backup verification, recovery testing, account administration, and incident response. Development and security resources will address defects and prioritize future improvements as needed.

LAME will provide legacy-system documentation and support investigation of compatibility issues that emerge after deployment. PITA will help define security monitoring, incident escalation, access-control reviews, and periodic verification of security controls. These responsibilities will be incorporated into the operational handoff rather than ending abruptly when the implementation project closes.

Project closeout will include formal acceptance of the agreed deliverables, completion of technical and operational documentation, transfer of responsibilities, and a lessons-learned review. The project manager will document unresolved issues and recommendations for future development.

The maintenance plan will establish responsibility for routine tasks, incident escalation, backups, recovery procedures, security reviews, and future enhancements. These ongoing activities will be managed separately from the 12-week implementation schedule and will require an operational budget after project closeout.

## Conclusion

The Frosmear Legacy Modernization project uses a 12-week schedule, an estimated $210,000 budget, and a capable cross-functional team to establish Darfcloud as a maintainable, secure application platform. The plan connects the seven phases of the work breakdown structure from Module 3 with resource allocation, stakeholder engagement, change control, deployment, and maintenance.

The LAME team will protect legacy compatibility and help preserve relevant functionality, while the PITA team will focus on security, data integrity, and threat prevention. Their early involvement allows the project to address technical and security concerns while development proceeds in parallel. Scope controls, timely decisions, and a contingency reserve will help manage the aggressive delivery schedule.

The project will be considered successful when the agreed initial release is tested, accepted, deployed, and transferred to operational ownership by December 23, 2026, providing a foundation for further Darfcloud development in FY2027.
